# JJJ-general-async-comm 异步沟通初始化技能

> 本 skill 是**通用异步沟通**（v1.2），不假设在代码项目中使用。
> 如需**开发场景专用**异步沟通治理流程（含 Git PR 治理、CI 验证、post-merge gate），请使用 [JJJ-dev-async-comm](../JJJ-dev-async-comm/SKILL.md)。

在指定文件夹创建异步沟通所需的标准文档结构，并提供任务管理流程。

## 整体流程

```
用户触发技能
    ↓
创建 async_comm 文档结构 (USER/TASK/Q&A/REGRESSION/RETROSPECTIVE)
    ↓
创建定时任务 (每5分钟执行)
    ↓
┌─────────────────────────────────┐
│ 定时任务执行 SOP                │
│                                 │
│ 1. 回归测试 → 检查 REGRESSION   │
│ 2. 任务执行 → 从 TASK.md 取任务  │
│ 3. 回归测试 → 检查 RETROSPECTIVE │
│ 4. 复盘沉淀 → 写 RETROSPECTIVE │
│ 5. 归档已完成 → archive/      │
│ 6. 重置TASK占位符            │
│ 7. 输出结果                   │
└─────────────────────────────────┘
经验沉淀在 RETROSPECTIVE.md
```

## 快速开始

用户触发此技能时，直接说：

**请提供要初始化异步沟通的文件夹路径。**

同时告知用户：
> 初始化后，我将创建一个**5分钟一次**的定时任务，自动执行该项目的任务流程。

等待用户输入路径后，创建文档结构并设置定时任务。

## 第一步：创建文档结构

在用户提供的路径下创建：
```
路径/
└── async_comm/
    ├── USER.md          ← 用户写需求
    ├── TASK.md        ← 执行者任务
    ├── Q&A.md         ← 疑问记录
    ├── REGRESSION.md  ← 回归测试（功能检查）
    ├── RETROSPECTIVE.md ← 复盘记录（经验沉淀）
    └── archive/         ← 已完成任务归档
        └── 2026-05-06_1430_任务名称.md  ← 年月日_时分_任务概述
```

### archive目录结构（归档文件）

归档文件名格式：`YYYY-MM-DD_HHmm_任务概述.md`

示例：
```
archive/
├── 2026-05-06_1430_完成用户登录功能.md
├── 2026-05-06_1500_修复登录超时问题.md
└── 2026-05-07_0915_添加忘记密码功能.md
```

### 归档流程

1. **识别**：检测 TASK.md 中状态为 ✅ 的任务
2. **创建归档文件**：文件名 = `年月日_时分_任务名称.md`
3. **移动内容**：将任务从 TASK.md 移动到 archive/
4. **重置TASK**：用占位符恢复 TASK.md 到待填写状态

### TASK.md 占位符模板

```markdown
### P0 - 必做任务

⬜ [新增任务占位符]
- 验收标准：xxx
- 相关需求：USER.md 中的 P0-x
```

归档后用新占位符填补空位，用户可继续添加任务。

### 文档分工

| 文件 | 用途 | 执行频率 |
|------|------|----------|
| USER.md | 需求方填写目标 | 仅初始 |
| TASK.md | 执行者任务清单 | 仅初始+更新 |
| Q&A.md | 疑问记录 | 持续 |
| REGRESSION.md | 回归测试（功能是否正常） | 每次 |
| RETROSPECTIVE.md | 复盘记录（经验教训） | 每次 |

## 锁机制

### 加锁规则
- 领取任务时：在"锁"字段记录 `任务ID (领取时间, 15min超时)`
- 锁的作用：防止多实例重复领取同一任务
- 每次启动时：检查所有 in_progress 任务，如有超时则自动解锁并恢复为 pending

### 解锁条件
- 任务完成：清除锁
- 超时：锁自动失效，任务恢复为 pending
- 阻塞：锁保留，但超时机制同样适用

---

## 任务状态定义

| 状态 | 含义 | 可转换状态 |
|------|------|------------|
| `pending` | 待领取 | → in_progress |
| `in_progress` | 进行中 | → completed, blocked |
| `blocked` | 阻塞中（等待用户回答） | → in_progress, dropped |
| `completed` | 已完成 | （终态） |
| `dropped` | 已放弃 | （终态） |

### 状态转换规则

- 任务被领取时：pending → in_progress
- 任务遇到问题无法解决：in_progress → blocked
- 问题解决后继续：blocked → in_progress
- 任务正常完成：in_progress → completed
- 任务确认无法完成：blocked → dropped

### 阻塞超时机制

- 默认超时时间：48小时
- 超时处理：
  - 48小时用户未回答：降级为P2，排在同优先级最后
  - 72小时用户未回答：标记为dropped，跳过
- 超时降级的任务，用户回答后自动恢复优先级

### 任务领取规则

1. 优先级的严格顺序：P0 → P1 → P2
2. 同优先级内按进入时间正序（先到先服务）
3. 阻塞任务不参与排序，但超时时自动降级
4. 每次只领取一个任务，完成后才能领取下一个

## 完成流程

1. 读取TASK.md获取当前任务
2. **检查锁**：读取"锁"字段，如有任务ID，检查是否超时（15分钟）
   - 未超时：已有任务在执行，跳过
   - 已超时或无锁：可领取新任务
3. 领取任务时更新状态：pending → in_progress，同时加锁
4. 按验收标准逐项实现
5. 每项都要**实际验证**（不是只看代码）
6. 完成后更新状态为 in_progress → completed，清除锁
7. 循环直到所有任务完成

---

## 迭代衔接机制

### 检测新迭代

当执行者检测到 USER.md 发生变化时：
1. 检查 `currentIteration` 字段
2. 如果 `currentIteration` > TASK.md 中的当前迭代，说明进入新迭代
3. 将旧迭代所有任务标记为 completed
4. 开始执行新迭代的任务

### 迭代完成判断

当以下条件全部满足时，认为当前迭代已完成：
- 进行中任务表格为空
- 待执行任务表格为空
- 阻塞中任务表格为空
- 没有 in_progress 或 blocked 状态的任务

### 迭代完成后的行为

1. 在 RETROSPECTIVE.md 记录本次迭代的复盘
2. 在 USER.md 的迭代记录中更新迭代状态为"已完成"
3. 定时任务检测到当前没有活跃任务时，自动进入**等待状态**
4. 等待期间每5分钟检查一次 USER.md 是否有新版本
5. 收到新版本后继续执行

## 第三步：自动创建定时任务

初始化完成后，**技能会自动创建定时任务**（`*/5 * * * *`，每5分钟执行一次）。

使用 CronCreate 工具：
- `cron`: "*/5 * * * *"
- `prompt`: 异步沟通任务执行的完整流程（见下方模板）
- `recurring`: true
- **durable**: true（写入 `.claude/scheduled_tasks.json`，跨会话保留）

```json
{
  "id": "项目ID",
  "cron": "*/5 * * * *",
  "prompt": "异步沟通任务执行 SOP：\n\n## 1. 回归测试\n1. 检查 async_comm/REGRESSION.md 存在\n2. 逐项执行回归测试，更新状态\n3. 如有问题记录到 REGRESSION.md 的修复记录\n\n## 2. 版本检测\n1. 读取 async_comm/USER.md，检查 version 和 currentIteration\n2. 读取 async_comm/TASK.md，检查当前迭代号\n3. 如果 USER.md currentIteration > TASK.md 当前迭代：\n   - 将旧迭代所有任务标记为 completed\n   - 在 TASK.md 创建新迭代的任务区块\n   - 继续执行新任务\n\n## 3. 锁检测与任务领取\n1. 读取 async_comm/TASK.md 的"锁"字段\n2. 如果有锁且未超时（<15分钟）：已有任务在执行，跳过任务执行\n3. 如果锁已超时或无锁：清除过期锁，继续领取新任务\n4. 按优先级 P0→P1→P2 找到第一个 pending 状态的任务\n5. 领取任务：更新为 in_progress + 加锁（记录当前时间）\n6. 用web-access验证（必须实际点击）\n7. 完成后更新状态为 completed，清除锁，归档到 archive/\n8. 循环直到所有任务完成\n\n## 4. 迭代完成判断\n当以下条件全部满足时，认为当前迭代已完成：\n- 进行中任务表格为空\n- 待执行任务表格为空\n- 阻塞中任务表格为空\n迭代完成后进入等待状态，每5分钟检查一次 USER.md 是否有新版本。\n\n## 5. 复盘沉淀（关键！）\n1. 检查 async_comm/RETROSPECTIVE.md 存在\n2. 回顾本次任务执行的关键决策和收获\n3. 将经验记录到 RETROSPECTIVE.md 的复盘表\n4. 格式：日期 + 迭代 + 任务阶段 + 经验/教训 + 可复用点\n5. 这些经验供未来同类型工作参考\n\n## 6. Q&A记录\n- 有任何新的想法，记录到 async_comm/Q&A.md\n- 当遇到不确定的问题，记录到「待回答问题」表\n\n## 执行原则\n- 每次执行严格按照 SOP 顺序\n- 检测版本变化是第一步，决定是否进入新迭代\n- 复盘是经验沉淀的关键环节，必须执行\n- 任务内容来自 TASK.md，不要硬编码",
  "recurring": true,
  "durable": true
}
```

**说明**：
- `durable: false`（默认）：只创建lock文件，会话结束后失效
- `durable: true`：创建lock文件 + 写入 `.claude/scheduled_tasks.json`，7天后自动过期

## 核心原则

### 角色分工
- **用户（需求方）**：只写 USER.md，不看 TASK.md 具体内容
- **执行者**：只看 TASK.md，按验收标准执行，不读 USER.md
- **监督者**：检查 USER.md 和 TASK.md 对齐性

### 文档流转
1. 用户在 USER.md 写需求
2. 监督者把需求转成 TASK.md 的验收标准
3. 执行者按 TASK.md 执行，完成后标记✅
4. 执行中的疑问记在 Q&A.md

### 优势
- 用户只需表达"要什么"，不用关心具体怎么做
- 执行者不用担心任务丢失，阅读顺序自上而下
- 监督者保证需求不丢失，执行方向不跑偏
