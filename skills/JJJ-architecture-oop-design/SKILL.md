## 核心框架：四大核心概念

面向对象设计围绕四个基础概念展开：

| 概念 | 定义 | 目的 |
|------|------|------|
| **抽象 (Abstraction)** | 提取对象的关键属性和行为，忽略无关细节 | 简化复杂度，聚焦本质 |
| **封装 (Encapsulation)** | 将数据+方法绑定在类中，对外隐藏实现 | 保护内部状态，提供接口 |
| **分解 (Decomposition)** | 将整体划分为更小、更独立的部件 | 职责分配，便于管理 |
| **泛化 (Generalization)** | 通过继承共享公共属性和行为 | 减少重复，提高复用 |

---

## 一、抽象 (Abstraction)

### 核心思想
在给定上下文中，提取对象最关键的属性与行为，忽略与目标需求无关的细节。

### 判断标准
- **属性**：对象的静态特征（如名称、ID、状态）
- **行为**：对象可执行的操作（如学习、吃饭）
- 同一概念在不同上下文中抽象不同（如"人"在餐厅vs医院）

### 实践要点
- 先抽象，后编码
- 根据需求决定抽象范围，避免过度设计
- 抽象随需求变化而迭代

## 二、封装 (Encapsulation)

### 核心思想
将数据（属性）和操作（方法）统一封装在同一个类中，对外只提供接口，隐藏内部实现。

### Java实现
```java
public class Student {
    // 私有属性 - 隐藏
    private double gpa;

    // 公共方法 - 对外接口
    public void setGPA(double newGPA) {
        if (newGPA >= 0.0 && newGPA <= 4.0) {
            this.gpa = newGPA;
        }
    }

    public double getGPA() {
        return this.gpa;
    }
}
```

### 访问修饰符

| 修饰符 | 访问范围 |
|--------|----------|
| `public` | 所有类可访问 |
| `protected` | 本类、子类、同包可访问 |
| `default` | 同包可访问 |
| `private` | 仅本类可访问 |

### 好处
- 数据安全：防止外部直接修改内部状态
- 实现隔离：内部实现可自由修改，不影响外部调用
- 易于维护：接口不变，内部可自由迭代

## 三、分解 (Decomposition)

### 核心思想
将一个复杂整体划分为更小、更易理解的部件，明确部件之间的职责与关系。

### 三种关系类型

| 关系 | UML符号 | 含义 | 代码表现 |
|------|---------|------|----------|
| **关联 (Association)** | 直线 | 两个独立对象有松散的使用关系 | 对象相互引用，可独立存在 |
| **聚合 (Aggregation)** | 空心菱形 | "has-a"关系，部分可独立于整体 | List等容器存放"部分" |
| **组合 (Composition)** | 实心菱形 | "强拥有"，部分与整体生死耦合 | 在构造器中直接实例化 |

### 示例

```java
// 关联：学生使用运动，双方独立存在
Student student = new Student();
Sport sport = new Sport();

// 聚合：课程拥有学生列表，学生可离开
public class CourseSection {
    private List<Student> students; // 学生属于课程但可独立存在
}

// 组合：房子拥有房间，房间不能独立于房子
public class House {
    private List<Room> rooms;
    public House() {
        this.rooms = new ArrayList<>(); // 房间随房子创建而创建
    }
}
```

## 四、泛化 (Generalization)

### 核心思想
通过继承将多个类的共同属性和行为抽取到父类中，减少重复代码。

### 继承 vs 接口

| 特性 | 继承 (extends) | 接口 (implements) |
|------|---------------|-------------------|
| 复用方式 | 复用父类属性和方法 | 只声明方法签名 |
| 多重实现 | 单继承 | 可实现多个接口 |
| 使用场景 | "是什么" (is-a) | "能做什么" (can-do) |

### UML表示
- **继承**：实线 + 空心箭头（指向父类）
- **接口实现**：虚线 + 空心箭头（指向接口）

### Java实现

```java
// 抽象类 - 不能直接实例化
public abstract class Animal {
    protected String name;
    public abstract void speak();
}

// 继承 - extends
public class Dog extends Animal {
    @Override
    public void speak() {
        System.out.println("汪汪");
    }
}

// 接口 - implements
public interface Flyable {
    void fly();
}

public class Bird implements Flyable {
    @Override
    public void fly() {
        System.out.println("飞翔中...");
    }
}
```

### 判断口诀
1. 需要成为多种类型 → 接口
2. 描述"是什么" → 继承
3. 描述"能做什么" → 接口
4. 需要复用大量代码 → 继承

## 设计原则

### 耦合度评估 (Coupling)

| 维度 | 目标 | 说明 |
|------|------|------|
| **Degree** | 低 | 模块间连接数量尽量少 |
| **Ease** | 易 | 无需了解内部实现即可交互 |
| **Flexibility** | 高 | 方便替换成更优模块 |

### 内聚度评估 (Cohesion)

| 级别 | 说明 |
|------|------|
| **高内聚** | 模块职责单一、意图清晰 |
| **低内聚** | 模块承担多重职责，应拆分 |

### 目标：低耦合、高内聚

### 其他关键原则

| 原则 | 说明 |
|------|------|
| **信息隐藏** | 对外只暴露最小必要信息 |
| **关注点分离** | 不同职责分到不同类/模块 |
| **概念完整性** | 系统风格统一，如出一人 |

## 设计流程

```
1. 需求获取
   ↓ 询问用户核心需求和约束
2. 概念设计
   ↓ 识别对象、职责、关系（高层抽象）
3. 技术设计
   ↓ 明确属性、方法、继承关系、接口
4. 实现
```

### 概念设计 → 技术设计示例

| 阶段 | 输出 |
|------|------|
| 概念设计 | 识别出"订单"、"用户"、"支付"三个实体对象 |
| 技术设计 | 明确Order类包含哪些属性和方法，User类与Order的关联关系 |

+------------------+
|     ClassName    |  ← 类名

## UML序列图 (Sequence Diagram)

### 核心元素

| 元素 | 含义 |
|------|------|
| **Actor/对象** | 参与者，以方框或小人表示 |
| **Lifeline (生命线)** | 对象下方的虚线，代表生存期 |
| **Activation (激活条)** | 对象处理消息时的活动时段 |
| **消息箭头** | 实线=调用，虚线=返回 |

### 高级结构

| 结构 | 说明 |
|------|------|
| **alt** | 条件分支（互斥条件） |
| **loop** | 循环（满足条件时重复） |

### 示例：电视换频道

```
TV Viewer → Remote: 按下频道号
Remote → TV: 切换频道
TV → TV Viewer: 显示画面
```

## UML状态图 (State Diagram)

### 核心元素

| 元素 | UML符号 | 说明 |
|------|---------|------|
| **初始状态** | 实心圆 | 起点 |
| **终止状态** | 实心圆外套圆 | 终点 |
| **状态** | 圆角矩形 | 对象的状态 |
| **转移** | 箭头 | 状态变更路径 |

### 活动类型

| 类型 | 说明 |
|------|------|
| **entry** | 进入状态时执行 |
| **exit** | 离开状态时执行 |
| **do** | 在状态中持续执行 |

### 守卫条件 (Guard)
转移箭头上的条件，如 `total >= price`

### 示例：自动售货机

```
idle --insert coin--> idle (金额不足继续等)
idle --insert coin--> enough_coins (金额足够)
enough_coins --dispense--> idle (完成交易)
any --cancel--> idle (取消退款)
```

## 继承问题与Liskov替换原则

### Liskov替换原则 (LSP)
子类对象必须能在所有需要父类对象的场合无差别工作。

### 继承误用案例

| 案例 | 问题 |
|------|------|
| **Stack extends Vector** | Stack获得不该有的列表操作，违背概念 |
| **Whale extends Animal** | Animal有walk()，Whale无法实现 |
| **Pizza extends Pizza** | 只是多了配料，用属性即可 |

### 继承判断标准
- 子类"是"父类的一种特殊化 (IS-A)
- 子类对父类行为进行了合理扩展或重写
- 不违背父类的语义契约

### 替代方案：分解+组合
当继承不合适时，将功能拆分到独立类，通过组合实现。

## 编程范式演变

### 历史脉络

| 时代 | 范式 | 特点 |
|------|------|------|
| 1960s | 命令式 (COBOL/Fortran) | 全局数据+子例程 |
| 1970s | 局部变量+抽象数据类型 | 数据封装 |
| 1970s-80s | 模块化 (C/Modula-2) | 文件分离+头文件声明 |
| 1980s+ | 面向对象 (Java/C++/C#) | 类+继承+封装 |

### 为什么OOP成为主流
- 硬件性能提升，人力成本成为主要瓶颈
- OOP让代码更贴近现实世界概念
- 提升可维护性和可扩展性

## 模型检查 (Model Checking)

### 核心概念
通过穷举分析系统所有可能状态，检测是否存在逻辑缺陷。

### 三阶段流程

| 阶段 | 说明 |
|------|------|
| **建模** | 描述系统行为与期望属性 |
| **运行** | 穷举遍历所有状态转换 |
| **分析** | 检查是否存在反例 (Counterexample) |

### 关键术语

| 术语 | 说明 |
|------|------|
| **State Model** | 状态模型（变量值+事件转移） |
| **Desired Properties** | 必须满足的正确性属性 |
| **Counterexample** | 证明系统会出错的执行序列 |

### 挑战
- **状态空间爆炸**：状态数指数增长，难以全面搜索
- **模型抽象**：需恰当抽取关键部分减小状态空间

### 适用场景
- 并发系统
- 通信密集型系统
- 安全关键系统

## 常见问题

### Q: 什么时候用继承 vs 接口？
- 有大量代码需要复用 → 继承
- 只需要定义行为契约 → 接口
- 需要多重类型 → 接口

### Q: 如何判断类的职责是否单一？
- 该类只有一个变化原因
- 类的名称能准确描述其职责
- 类的方法都服务于同一个目标

### Q: 聚合和组合怎么选？
- 部分可独立存在 → 聚合
- 部分属于整体、不可分离 → 组合

### Q: CRC卡和类图有什么区别？
- CRC卡：概念设计阶段，侧重职责和协作
- 类图：技术设计阶段，包含属性类型和方法签名

### Q: 什么时候用序列图 vs 状态图？
- 序列图：展示多个对象的交互顺序
- 状态图：展示单个对象的状态变迁
