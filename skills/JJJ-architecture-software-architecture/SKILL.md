## 架构概述

### 什么是软件架构

软件架构是系统的**整体高层设计**，决定系统组件如何协作，影响开发效率、质量和可维护性，并需兼顾多方利益相关者与技术可行性。

**类比**：建筑师设计摩天大楼——考虑用途、使用者、质量要求、场地约束；软件架构师同样考虑系统用途、用户、关键质量属性、运行环境。

### 架构与设计模式的关系

- **设计模式**：针对单一技术问题提供解决方案（如可维护性、性能、复用性）
- **架构**：着眼于**整体系统问题**，协调多个设计模式，确保系统一致性，解决设计模式无法覆盖的质量属性

## Kruchten 4+1 视图模型

Philippe Kruchten 的四加一视图模型从多个角度理解软件系统架构。

### 五个视图

| 视图 | 关注点 | UML工具 | 核心元素 |
|------|--------|---------|----------|
| **逻辑视图 (Logical)** | 功能实现、满足客户需求 | 类图 | 系统对象、类、属性、方法 |
| **过程视图 (Process)** | 非功能要求（性能、可用性） | 序列图、活动图 | 对象执行顺序、方法调用顺序、异步/并发行为 |
| **开发视图 (Development)** | 软件实现及开发管理 | 组件图、包图 | 层级结构、编程语言、库、工具集 |
| **物理视图 (Physical)** | 系统部署到硬件环境 | 部署图 | 硬件节点映射、物理组件交互 |
| **场景视图 (Scenarios)** | 连接四个视图，验证系统功能 | 用例图 | 脚本描述对象与过程交互顺序 |

### 场景视图作用

场景（Scenarios）将四个视图联系起来，用脚本描述对象与过程交互顺序。例如聊天应用：聊天框&输入框 → 发送消息&接收消息流程。

**记忆口诀**：功能看逻辑，性能看过程，开发管理看开发，部署看物理，场景贯穿四者。

## UML建模图

### 组件图 (Component Diagram)

**用途**：高层次展示系统组件及其交互关系，静态视图，不关注具体实现。

**核心元素**：
- **Provided Interface (球形标记)**：组件提供给其他组件的交互接口
- **Required Interface (插口标记)**：组件需要其他组件提供的接口
- **装配关系**：Provided与Required接口匹配，球-插口连接

**绘制步骤**：
1. 识别系统主对象
2. 确定相关库及第三方依赖
3. 确定组件间关系

**银行系统示例**：
```
Client → BankService(Facade) → CheckingAccount, SavingAccount, InvestmentAccount
                           ↓
                      IAccount接口
```

---

### 包图 (Package Diagram)

**用途**：对系统中的相关元素进行分组管理，展示包与包之间及包内元素的依赖关系。

**核心元素**：
- **带标签的文件夹**：表示包，包名居中
- **Public (+)**：外部可访问
- **Private (-)**：外部不可访问，仅限包内

**包间关系**：
- **Import (导入)**：将另一个包的元素引入当前包，可设置public/private
- **Merge (合并)**：将两个包或概念合并为一个
- **Uses (使用)**：一个包依赖另一个包完成其功能

**游戏系统示例**：
```
Player包: +Movement, -Accounts, -Levels
Level包: uses Player包, import public Player:Location
User Interface包: import public Player
NPC包: merge Vendors, Quest-givers
```

---

### 部署图 (Deployment Diagram)

**用途**：可视化软件系统的部署环境、部署目标及其内部构件（Artifacts）。

**核心元素**：
- **Node (节点)**：部署目标或软件执行环境，3D盒子表示
- **Artifact (工件)**：开发过程的物理产物（可执行文件、安装程序、音频库）
- **Manifestation (实现)**：Artifact物理实现软件组件

**两种级别**：
| 类型 | 说明 |
|------|------|
| **规格级 (Specification Level)** | Artifact与部署目标概览，不涉及具体机器名称 |
| **实例级 (Instance Level)** | 精确映射Artifact→部署目标，可标识特定硬件 |

**视频游戏部署示例**：
```
[MacBook Pro节点]
  ├── artifact "Game Executable"
  └── artifact "Audio Library"

[Windows PC节点]
  ├── artifact "Game Executable"
  └── artifact "Audio Library"

MacBook Pro --> Server: HTTPS
Windows PC --> Server: HTTPS
```

---

### 活动图 (Activity Diagram)

**用途**：可视化系统中活动的控制流、条件分支和并发流程。

**图形元素**：
- **起始节点 (●)**：标示流程开始
- **结束节点 (◎)**：标示流程结束
- **中间活动 (圆角矩形)**：描述改变状态的动作
- **决策节点 (◇)**：条件分支，一条进入多条输出
- **分叉节点 (|)**：一条流分为多条并行流
- **合并节点 (|)**：多条并行流汇合为一条

**并发示例（Cookie Clicker游戏）**：
```
[开始游戏] → [关卡1] → [决策:分数>=50?] → 是 → [奖励关卡]
                                        ↓ 否
                                      [游戏结束]

同时：[关卡1] → [播放音轨] → [游戏结束]  （并行）
```

**泳道 (Swim Lanes)**：按角色或模块分组活动，例如玩家动作一条泳道，系统活动一条泳道。

## 架构风格 (Architectural Styles)

### 1. 主程序与子程序 (Main Program & Subroutine)

**来源**：过程式编程范式，典型语言C

**核心概念**：
- 系统拆分成主程序和子程序
- 子程序通过过程调用互相连接，可嵌套调用
- 代码结构呈层级化，可视为有向图或调用树

**数据管理**：
- **局部变量**：每个子程序可有自己的局部变量
- **参数传递**：by value/by reference传入子程序
- **返回值**：通过返回值传出

**设计原则**：
- **一入口一出口**：保证子程序控制流清晰
- **函数黑箱**：给定输入，保证输出可预测
- **全局变量风险**：子程序可能改变全局数据，影响其他子程序

**支出管理程序示例**：
```
主程序
  ├── parseRecords() → 解析购买记录
  ├── categorizeExpenses() → 分类求和
  ├── sumTotal() → 总和计算
  └── generateReport() → 报告生成
```

---

### 2. 分层架构 (Layered Architecture)

**核心**：层间交互限制，组件只能与同层或相邻层交互。

**学校类比**：
```
        [校长/Principal]
              │
        [教师/Teacher Layer]
              │
    ┌──────────┴──────────┐
[学生/Student Layer]  [系统库/Library Layer]
```

**层间交互规则**：
- 下层提供服务或抽象给上层
- 上层请求信息或操作，下层提供响应
- 可允许**pass-through**交互（非相邻层直接通信，但会增加耦合）

**操作系统实例**：
| 层级 | 职责 | 示例 |
|------|------|------|
| 内核层 (Kernel) | 硬件接口、资源分配 | 处理器调度、鼠标输入 |
| 系统/应用库层 | 提供高层功能 | 文件保存、图形绘制 |
| 用户应用层 | 命令行工具、GUI程序 | 用户安装的软件 |

---

### 3. n层架构 (n-Tier Architecture)

**与分层架构的区别**：Layered是逻辑分层，n-Tier通常对应不同物理机器，强调物理分布。

**Client-Server模式**：
- **Server**：提供服务（数据库存储、计算任务）
- **Client**：发送请求，Server返回响应
- **通信方式**：
  - **同步 (Synchronous)**：Client等待响应，UML闭合箭头
  - **异步 (Asynchronous)**：Client发请求后立即返回，线箭头，Server完成后回调

**2-Tier架构示例（家用媒体服务器）**：
```
[平板Client] ──请求──> [媒体Server]
                          │ 存储、流式传输
                          ↓
                    [可执行文件、音频库]
```

**3-Tier架构与中间层**：
```
[客户端] → [中间层/Business Logic] → [数据库Server]
   │              │                    │
   │         应用逻辑、安全           数据存储
   │         业务流程处理
   ↓
展示(Presentation)
```

**优缺点**：
| 优点 | 缺点 |
|------|------|
| 可扩展性：增加客户端或层数 | 资源消耗：额外管理客户端/服务器关系 |
| 集中化：数据、计算力集中管理 | 复杂性增加：不同机器和通信协议带来维护难度 |
| 分离关注点：每层关注单一职责 | 单点故障：Server层故障影响整体 |
| 松耦合：层与层之间接口明确 | 效率问题：严格层通信可能增加传递开销 |

### 4. 面向对象架构 (Object-Oriented Architecture)

**核心原则**：抽象、封装、分解、泛化

**系统建模方法**：
- **抽象数据类型 (ADT)**：通过类组织数据属性和方法
- **类与对象**：类实例化生成对象，通过方法交互
- **继承扩展**：一个抽象数据类型可扩展另一个类型

**自动宠物喂食器案例**：
```java
// Pet类：管理宠物信息和食物摄入
public class Pet {
    private String collarID;

    public void updateIntake(int amount) {

    public void resetIntake() {
        currentFoodIntake = 0;
    }
}

public class FoodDispenser {

    public void dispenseFood(String petId, int amount) {
        if (authorizedPets.contains(petId) && amount <= remainingFood()) {

        }
    }
}
```

### 5. 数据中心架构 (Data-Centric Architecture)

**核心概念**：
- **中央数据组件 (Central Data)**：存储并提供数据给所有连接的组件，通常是数据库
- **数据访问器 (Data Accessor)**：连接数据库，执行查询与事务，独立操作，功能间互不直接通信

**优势**：
- 模块化：各访问器独立，业务逻辑分离
- 可扩展性：增加访问器无需担心影响其他组件
- 可维护性：功能和数据分离，便于管理
- 减少直接通信开销：组件之间通过数据库间接通信

**风险**：
- **单点依赖**：中央数据组件宕机或损坏影响整个系统
- **数据库依赖**：添加访问器需遵循现有数据模式(Schema)

**企业系统示例**：
```
[时间表系统访问器] ──┐
[薪酬系统访问器] ────> [中央数据库] ←── 用户权限管理
[考勤系统访问器] ──┘
```

### 6. 管道和过滤器 (Pipe and Filter)

**核心**：数据流架构，数据通过多个过滤器变换。

**组成**：
- **Filters (过滤器)**：独立实体，对接收到的数据执行变换（输入→处理→输出）
- **Pipes (管道)**：数据传输连接器，将前一过滤器输出传递给下一过滤器

**数据流示例**：
```
[Data Source] → |Filter 1: 净化| → |Filter 2: 加热| → [Data Target]
                                       ↓
                              输出: 净化后的热水
```

**关键原则**：
- **顺序决定结果**：对数学计算或数据处理，顺序决定最终结果
- **每个过滤器只关注自己的输入和输出，不依赖其他过滤器内部状态**

**UNIX文本处理示例**：
```bash
cat file.txt | grep "error" | sort | uniq
# 数据源 → 过滤(grep) → 过滤(sort) → 过滤(uniq) → 数据目标
```

**优缺点**：
| 优点 | 缺点 |
|------|------|
| 松耦合：过滤器独立运行 | 性能开销：每个过滤器需解析输入执行变换 |
| 黑箱操作：无需了解过滤器内部逻辑 | 数据过载：某些过滤器处理大量数据可能产生瓶颈 |
| 复用性：过滤器可多次调用处理不同输入 | 交互性不足：不适合需要快速响应的交互式应用 |

### 7. 事件驱动架构 (Event-Driven Architecture)

**核心**：系统的核心元素是事件（signals, user inputs, messages）。

**关键概念**：
- **事件生成器 (Event Generator)**：发出事件
- **事件消费者 (Event Consumer)**：接收并处理事件
- **事件总线 (Event Bus)**：中介，连接所有事件生成器与消费者

**隐式调用 (Implicit Invocation)**：
- 传统函数调用是显式调用
- 事件驱动函数通过事件总线触发，函数不直接调用其他函数

**实现步骤**：
1. 消费者在事件总线上注册关注的事件
2. 总线检测到事件后，通知所有相关消费者

**Cookie Clicker游戏案例**：
```
手动点击cookie → 生成click事件 → 增加1点cookie
购买自动点击器 → 注册定时器事件生成器(每5秒触发) → 增加对应cookie数量
```

**异步处理与竞争条件**：
- **竞争条件 (Race Condition)**：共享数据更新顺序不确定，导致行为依赖调用顺序
- **信号量 (Semaphore)**：二值信号量(available/unavailable)解决共享数据访问

**虚拟代理 vs 保护代理 vs 远程代理**

| 类型 | 用途 | 示例 |
|------|------|------|
| **虚拟代理** | 延迟创建资源密集型对象 | 图片懒加载、网页加载 |
| **保护代理** | 控制访问权限 | 根据角色检查权限 |
| **远程代理** | 操作远程对象 | Google Docs浏览器端操作远程服务器对象 |

### 8. 发布-订阅架构 (Publish-Subscribe)

**与事件驱动架构的区别**：
1. 组件要么是发布者，要么是订阅者，不能同时是两者
2. 发布者和订阅者之间的关系在形式和密切程度上有所不同

**实现方式**：
- 订阅者通过回调向发布者登记兴趣
- 发布者维护订阅者列表，通过已注册回调的过程调用与订阅者通信
- 可引入连接器（事件总线或网络协议）处理大规模应用

**邮件列表/RSS订阅示例**：
```
发布者 → 事件总线 → 订阅者1, 订阅者2, ...
              ↓
         连接器可过滤信息
```

### 9. 解释器架构 (Interpreter)

**核心**：系统中内置解释器，将用户输入的语言、公式或指令翻译成中间表示并执行。

**可编程应用实现步骤**：
1. 用户输入命令或公式（如 `SUM(A1:A4)`）
2. 解释器将其翻译成中间表示（Intermediate Representation）
3. 系统执行该中间表示，返回计算结果

**脚本 vs 宏**：
- **脚本 (Script)**：用户编写的序列化指令，用于自动化重复任务、组合复杂任务
- **宏 (Macro)**：基于GUI的操作录制，记录键盘和鼠标输入

**性能优化（JVM示例）**：
```java
// Java程序先编译为Bytecode
// JVM执行Bytecode时监控执行频率
// 高频指令即时编译(JIT)为机器码执行
// 低频指令继续由解释器执行
// 使用Lazy Linking避免重复编译
```

### 10. 状态转换系统 (State Transition System)

**核心概念**：
- **状态 (State)**：系统记忆的信息定义系统状态
- **过渡 (Transition)**：系统从一种状态到另一种状态的变化
- **行为 (Behavior)**：系统在遇到定时事件或用户输入时做什么

**无标签 vs 有标签**：
- **无标签**：状态对S和转换对→，若p→q则p转换到q
- **有标签**：包含标签集，转换表示为p⭇q

**队列系统示例**：
```
[空] ←→ [排队中] ←→ [满]
  ↑___________↑
  (可容纳多个对象)
```

**实际应用**：
- 资源分配：确定资源使用发生时间、哪些进程使用、资源使用多久
- 并行处理/多线程/分布式：系统状态建模
- 死锁识别：阻止从特定状态转换的条件出现即死锁

### 11. 过程控制架构 (Process Control)

**反馈循环 (Feedback Loop)**：
```
[温度传感器] → [控制器软件] → [加热通风口] → [房间温度]
     ↑____________________________________________|
                    反馈
```

**四个基本组件**：
| 组件 | 说明 | 示例 |
|------|------|------|
| **传感器 (Sensor)** | 检测实际值 | 温度传感器 |
| **控制器 (Controller)** | 软件逻辑，比较实际值与目标值 | 计算Error = SetPoint - Actual |
| **执行器 (Actuator)** | 物理手段改变过程 | 加热通风口 |
| **过程 (Process)** | 被控制对象 | 房间本身 |

**控制器类型**：
- **开环 (Open Loop)**：无过程监控，简单但无法应对变化（如旧式烘干机固定时间运行）
- **闭环 (Closed Loop)**：反馈信息用于控制同一过程，可自动调整应对变化
- **前馈控制 (Feedforward)**：基于上游过程信息控制下游过程，要求精确模型

**MAPE-K架构（复杂系统）**：
| 步骤 | 说明 |
|------|------|
| **Monitor** | 收集并转化传感器数据 |
| **Analyze** | 整合多传感器信息，构建过程行为模型 |
| **Plan** | 根据模型预测结果决定操作策略 |
| **Execute** | 将规划转化为执行器信号 |
| **Knowledge** | 存储过程模型与规则的核心支撑组件 |

## 质量属性 (Quality Attributes)

### 定义

可量化的系统特性，用于评估设计、运行和可用性。

### 主要质量属性

| 属性 | 定义 | 测量方法 |
|------|------|----------|
| **可维护性 (Maintainability)** | 系统易于修改，修复错误、添加新功能或淘汰旧功能 | 变更所需时间、影响范围 |
| **可复用性 (Reusability)** | 系统功能或模块能在其他系统中重复使用 | 复用次数、适配成本 |
| **灵活性 (Flexibility)** | 系统适应未来需求变化的能力，及时且成本可控 | 变更难度、所需资源 |
| **可修改性 (Modifiability)** | 系统修改或新增功能的便利性 | 修改范围、测试成本 |
| **可测试性 (Testability)** | 系统可通过可执行测试快速识别错误 | 覆盖率高、问题定位速度 |
| **概念完整性 (Conceptual Integrity)** | 设计在子系统间保持一致性，命名规范统一 | 一致性检查结果 |
| **可用性 (Availability)** | 系统运行时间占比，衡量故障恢复能力 |正常运行时间/总时间 |
| **互操作性 (Interoperability)** | 系统与外部系统交换信息的能力 | 协议兼容性、数据格式支持 |
| **安全性 (Security)** | 防止未授权访问，保证数据完整性 | 攻击成功率、漏洞数量 |
| **性能 (Performance)** | 系统响应速度和吞吐量 | 延迟(ms)、吞吐量(输出/时间) |
| **易用性 (Usability)** | 系统直观易用、减少用户操作错误、提供反馈 | 完成任务时间、错误率 |

### 利益相关者视角

| 关注点 | 开发团队 | 终端用户 |
|--------|----------|----------|
| 关注 | 可维护性、可复用性、可测试性、支持性 | 易用性、错误处理、系统稳定性、体验 |

## 架构评估方法 (ATAM)

### ATAM (Architecture Tradeoff Analysis Method)

**优势**：评估者无需熟悉系统架构或问题空间，可由设计者、同行或外部专家进行评估。

### 参与者

| 角色 | 说明 |
|------|------|
| **评估团队** | 设计者、同行、外部专家，要求无偏见 |
| **项目决策者** | 项目经理、客户、产品负责人、架构师、技术负责人 |
| **架构利益相关者** | 最终用户、开发者、支持人员 |

### ATAM九步流程

1. **Present ATAM**：说明上下文、期望、流程与输出
2. **Present Business Drivers**：决策者介绍业务问题、系统目标、功能、约束和范围
3. **Present Architecture**：展示现有与预期架构状态及项目约束
4. **Identify Architectural Approaches**：分析已用架构模式，提出问题获取清晰信息
5. **Create Quality Attribute Utility Tree**：
   - 将质量相关需求(ASRs)拆分并优先级排序(H/M/L)
   - **Refinements**：将通用质量属性细化为具体属性
6. **Analyze Architectural Approaches**：
   - 用优先级ASRs检查架构是否满足要求
   - **识别风险/非风险场景、敏感点、权衡**
7. **Brainstorm & Prioritize Scenarios**：各参与组创建、合并场景，优先级匹配ASRs
8. **Reanalyze Architectural Approaches**：使用前五至十个优先场景更新utility tree
9. **Present Results**：汇总风险场景、风险主题、敏感点、权衡、所有文档

### 关键概念

| 概念 | 说明 |
|------|------|
| **敏感点** | 高流量增加延迟等架构特性 |
| **权衡** | 限制并发用户数以降低延迟，但降低可用性 |
| **风险场景** | 可能导致系统问题的场景 |
| **非风险场景** | 系统能良好应对的场景 |

## Conway定律 (Conway's Law)

**定义**：系统会倾向于呈现出与创造它的组织结构一致的形式。

**组织结构与耦合度**：
- **松散组织（如开源项目）** → 模块化、低耦合
- **内部紧密团队** → 高耦合、模块边界不清晰

**哈佛商学院2007年研究（MacCormack等）**：
- 开源项目 → 松散耦合、模块化代码
- 内部团队 → 紧耦合代码

**应用**：
1. 先确定理想架构，再组织团队与任务分配
2. 设置专门团队统一服务和架构标准，防止"配对集成"问题
3. 利用Conway定律预见潜在耦合问题并设计架构缓冲层

**团队-架构对应示例**：
```
[系统架构: n-Tier]
     │
     ├── [数据后端] → 数据层团队
     ├── [应用逻辑层] → 应用逻辑团队 + 整合团队
     └── [表现层] → 表现层团队
```

## 软件产品线 (Software Product Line)

### 核心概念

**产品线/产品系列**：具有共同特征的一组产品，通过同时开发其共性来提高效率。

### 产品线特征分类

| 特征 | 说明 | 示例 |
|------|------|------|
| **Commonalities (共同特性)** | 所有产品一致的特性 | iPhone/iPad共享操作系统 |
| **Variations (可变特性)** | 部分产品存在的特性 | 不同网络连接支持 |
| **Product-specifics (产品特有)** | 只属于某一产品 | 电子书阅读器的电子墨水支持 |

### 团队划分

| 团队 | 职责 | 输出 |
|------|------|------|
| **Domain Engineering (领域工程)** | 构建产品的共同特性和可变特性 | 参考架构和通用组件 |
| **Application Engineering (应用工程)** | 利用领域工程提供的组件开发具体产品 | 具体产品实现 |

### 参考架构 (Reference Architecture)

**定义**：支撑整个产品线的基础架构，支持所有产品的共性特性，具备变化能力。

**变化实现技术**：
| 技术 | 说明 |
|------|------|
| **Adaptation (适配)** | 单一实现，通过接口或配置文件调整功能 |
| **Replacement (替换)** | 用默认组件或替代组件实现变化 |
| **Extension/Plugin (扩展/插件)** | 提供统一接口，支持多种扩展 |

**变异实现阶段**：
```
设计/开发阶段 → 编译/构建阶段 → 运行时加载阶段 → 动态加载阶段
```

### Apple iOS产品线示例

```
[iOS产品线参考架构]
     │
     ├── [共同特性] → 触摸交互、App Store、多点触控
     ├── [可变特性] → 电话功能(iPhone)、大屏布局(iPad)
     └── [产品特有] → 电子墨水(iPad阅读版)
```

## 架构设计原则

| 原则 | 说明 |
|------|------|
| **关注点分离 (Separation of Concerns)** | 将子系统按职责分离 |
| **信息隐藏 (Information Hiding)** | 控制子系统间暴露的信息 |
| **复用实现 (Implementation Reuse)** | 相同功能实现跨子系统共享 |
| **资源管理规则 (Resource Management)** | 明确使用内存、线程、带宽等策略 |

**资源管理示例**：在线商店中客户交易优先使用带宽，查询操作次之。

## 常见问题

### Q: 什么时候用分层架构 vs n层架构？
- 分层架构是逻辑分层，适合单一机器部署
- n层架构强调物理分布，适合需要扩展到多台机器的场景

### Q: 事件驱动 vs 发布-订阅的区别？
- 事件驱动：函数可兼任生成器和消费者
- 发布-订阅：组件只能是发布者或订阅者之一，关系更松散

### Q: 如何选择架构风格？
- 计算密集型 → 主程序与子程序
- 企业级多用户系统 → n层架构
- 数据共享强 → 数据中心架构
- 数据流处理 → 管道和过滤器
- 交互式应用 → 事件驱动

### Q: ATAM评估什么时候做？
- 架构设计初期：验证架构是否满足需求
- 重大变更前：评估变更影响
- 项目上线前：确保质量属性达标
